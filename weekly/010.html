Cursor Rulesを日本語で設計して
確実に動かす方法を調べた

Cursor Cursor Rules AI活用 チーム開発 日本語運用

📌 今回取り上げたもの

現状、Cursorによる工数削減を図るため実装などをCursorによって自動化を進めているが、実装の精度などの部分で完璧とはいいがたいと考えている。そこで、少しでも成果物の精度を上げることができる指示の出し方を検討した。

今回は「Rulesを日本語で書きながら、AIに確実に動いてもらうにはどうするか」を調査した。言語ポリシーの設計、モードの使い分け、効くRulesの書き方まで整理する。

🌐 ① まず言語ポリシーを設定する

なぜ必要か

日本語で指示を書いても、AIは内部的に英語に変換してから処理している。つまり日本語の指示 → 英語翻訳 → 推論 → 日本語で返答という経路をたどる。LLMは圧倒的な量の英語データで事前学習しているため、推論自体は英語の方が安定しやすい構造になっているためだ。

この背景があるため、日本語でRulesを書く前提でやりがちな設定がこれ：

Always respond in Japanese.

これだけだと過剰翻訳が起きる。内部翻訳の過程でコードの変数名・関数名まで日本語化しようとしたり、エラーログの引用ニュアンスが壊れたりする。「Always」の制約を文字通り守りすぎるのが原因だ。

複雑なロジックの組み立てや、バグの原因を追う処理は英語ベースの推論パターンの方が安定しやすい。これを無視して全部日本語に縛ると、推論精度が落ちる。

解決策：領域ごとに言語を分ける

内部推論
英語推奨
コード
（変数名・関数名・コメント）
英語のみ
チャット返答
ドキュメント・ラベル
日本語

この境界を明示するLanguage Policyルールを最初の1枚として必ず設ける。これが日本語Rulesを動かす前提条件になる。

📄 .cursor/rules/language-policy.mdc
--- alwaysApply: true --- ## 言語ポリシー - **内部推論（Chain-of-Thought）**: 英語推奨 - **コード（変数名・関数名・コメント）**: 英語のみ - **チャット返答・ドキュメント・ラベル・タスク名など**: 日本語

🔀 ② 4つのアクティベーションモード

`.cursor/rules/` 配下の `.mdc` ファイルは、フロントマターの書き方でいつ読み込まれるかが変わる。

💡 フロントマターとは：ファイルの先頭に書く設定情報のこと。--- で囲まれた領域に、そのファイルをいつ・どのように読み込むかを定義する。

モード フロントマター 読み込まれるタイミング
Always Apply alwaysApply: true 全リクエストで必ず読み込まれる
Auto Attached globs: ["src/**/*.tsx"] 該当ファイルを開いているとき
Agent Requested description: "..." のみ AIが文脈を読んで判断・自動適用
Manual フロントマターなし チャットで @ルール名 と書いたとき

注意点：alwaysApplyは使いすぎると重くなる。全リクエストでトークンを消費するため、プロジェクト全体で2〜3枚以内が目安。言語ポリシーと最低限のプロジェクト概要だけをalwaysApplyにして、それ以外はAutoまたはAgentにするのが基本設計になる。

旧 `.cursorrules`（ルートに1ファイル）は非推奨になっている。`.cursor/rules/*.mdc` に移行すること。

📁 ③ 何を書くか：4カテゴリ

Atlan社の実践をもとに整理した。ファイル数の目安は5〜8枚。多すぎると管理が崩れる。

Always ① プロジェクトルール
このプロジェクトが何か、ディレクトリ構造、用語集。Cursorが「どのリポジトリで作業しているか」を理解する地図になる。ここがないとAIは毎回コンテキストなしで動く。
Always / Auto ② 技術スタック・コーディング規約
フレームワーク・命名規則・コンポーネント構造など。「named exportのみ」「useEffectでデータ取得禁止」のようなチームの規約。特定ファイルにのみ適用したいものはAutoにする。
Agent Requested ③ マイクロワークフロー
チームの行動パターン。「ログをどう書くか」「DBマイグレーションに何を含めるか」「フィーチャーフラグをいつ使うか」など。コードの書き方ではなく、作業の進め方。AIが状況を読んで自動適用する。
Always ④ メタルール
他のルールをどう解釈・優先するか。「ルールが競合したときどちらを優先するか」「ルールにマッチしない状況でどうするか」。今回の言語ポリシーもここに分類される。

✍️ ④ 日本語で効くRulesの書き方

日本語で書いても動く。ただし書き方に原則がある。

断定形で書く

AIは曖昧な指示を無視しやすい。「〜してください」「〜が望ましい」ではなく「〜すること」「〜は禁止」で書く。

❌ 無視されやすい
propsの型はなるべく interfaceで定義してください 関数はできるだけ 短く保つよう心がけて default exportより named exportを検討してください
✅ 効く
propsの型は必ず interfaceで定義すること 関数は30行以内にすること named exportのみ使うこと （default exportは禁止）

1ファイル1テーマ、100行以内

1枚のファイルに複数のテーマを詰め込まない。100行を超えたら分割する。短いほうがAIが解釈しやすく、メンテナンスもしやすい。

重要な制約は末尾に書く

LLMはファイル末尾の内容を優先しやすい特性がある。「例外・絶対にやってはいけないこと」は末尾に書くと効果が上がる。

チャットから自動生成する

チャット中に「そう、それが正しい」と感じた瞬間に /Generate Cursor Rules を実行すると、その会話を元にルールファイルが自動生成される。一から書く必要がなく、実際の修正のやりとりがそのままRulesになる。

ルールが効いているか確認する

チャットで @ルール名.mdc と入力すると、そのルールを手動で強制適用してテストできる。「なぜか効かない」と感じたら、まずglobパターンのタイポを疑う（typoがあると無音で無視される）。

📋 まとめ：何から始めるか

日本語チームでCursor Rulesを導入する場合の優先順位。

順番 やること 理由
1 language-policy.mdc を作る（alwaysApply） これがないと日本語Rulesが過剰翻訳を引き起こす
2 プロジェクト概要ルールを作る（alwaysApply） AIがリポジトリのコンテキストを理解できるようになる
3 技術スタック・規約ルールをファイル種別ごとに作る（Auto） 必要なときだけ読まれるのでトークン効率がいい
4 月次でルールを見直す 古いルールがあると逆に精度が落ちる

💭 自分の考え・業務への活用案

コンフルの用語集のページと連携できるようになると、より案件の内容をAIに理解させやすくなるのではないかと感じた。ただ、これにはおそらくMCPが必要で、案件コンフルの内容を取得するMCPが実現した場合に転用できる内容だと考えている。

また、アクティベーションモードについて確認したところ、現状の設定ではAuto Attachedが設定されていた。歴史の長いプロジェクトではコードの修正に制限が設けられていることもあるため、すべてのリクエストに適用されるAlways ApplyやAIが自動判別するAgent Requestedは問題が発生しかねない。現状のAuto Attached設定が適切だと感じた。
